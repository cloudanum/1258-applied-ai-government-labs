# Sample / solution

## Why this approach works
Scoring against evidence, not effort, is what makes the checklist defensible: a 2 means you could hand an auditor the artifact today, not that someone is working on it, and a plan to build monitoring is honestly a 1. The discipline matters because pilots die on unglamorous items everyone assumed someone else owned, and the score's only value is forcing each gap to carry a next action and a named owner before production is discussed. The weaker instinct is the comfortable sweep of 1s and 2s with nothing behind the numbers, which converts the checklist into theater and lets the demo's momentum substitute for readiness. FISMA's continuous-monitoring model is the law behind the habit: authorization and readiness are not one-time events, so the lowest item is not an embarrassment to hide, it is the one artifact the debrief needs.

## A complete solution
A strict sample scoring of the five pinned items, for a pilot chat assistant answering citizen questions about benefit programs: monitoring scores 1, a dashboard exists but there is no weekly drift report with a named owner; evaluation scores 1, the pilot was demoed on twenty hand-picked questions but never scored against a versioned answer key; escalation path scores 0, nothing documents who a citizen contacts after a wrong answer or who can take the assistant offline; cost controls score 2, a monthly token budget with alerts is live in the finance system and could be shown to an auditor today; human review scores 1, a reviewer spot-checks answers informally but with no sampling plan or log.

The lowest item is the escalation path at 0, and it is also the one that would hurt most in public if it failed on day one, which is the tie-break rule if another item had scored 0 alongside it. The gap sticky in the capture template reads: "lowest item: escalation path (scored 0, no documented route for a citizen who gets a wrong answer) | next action: publish a one-page escalation SOP naming who can take the assistant offline and how a citizen reaches a human, then tabletop-test it once before launch | owner: the service delivery manager for the benefits portal."

Two defenses to be ready for in the debrief. First, monitoring at 1 rather than 2: the dashboard's existence is effort, while the README's bar for a 2 is a running weekly drift report with a named owner, which does not exist yet. Second, cost controls at 2 rather than 1: the budget and alerts are already live and inspectable, which is exactly the auditor-artifact standard. If a neighbor's lowest item is monitoring instead, that is a finding, not a mistake: it usually means their pilot has an escalation route on paper but no drift visibility, and the right response is to compare what evidence each score rested on.
