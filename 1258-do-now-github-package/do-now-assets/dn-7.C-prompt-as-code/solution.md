# Sample / solution

## Why this approach works
The header works because it converts a prompt from loose text into an artifact under change management: once a prompt has a name, a version, an owner, and a contract, an edit stops being invisible and starts being a deployment you can review, test, and roll back. The test case is the part that does the real work. Without it, a colleague can improve the wording tomorrow and silently break the output shape, and nobody finds out until a downstream reader complains. The weaker instinct, just writing the prompt more carefully or saving a copy with today's date in the filename, falls short because nothing trips when behavior changes: there is no expected output to compare against, and no version number to roll back to. Requiring `name/version | input | test` before any edit ships is the minimum bar that makes prompt drift detectable instead of silent.

## A complete solution
Take prompt P1 as an everyday working prompt: "Summarize this citizen email for the duty officer." As loose text it has no owner, no contract, and no tripwire. Wrapped in the minimum header, it becomes: name: citizen-email-summarizer; version: v1.0; owner: the 311 service analytics team lead; purpose: turn a raw citizen email into a three-sentence brief for the duty officer; inputs: one field, email_text, the raw message with PII left in place; output schema: JSON with exactly three keys, summary (string, at most three sentences), category (one of benefits, permits, complaint, other), urgency (one of low, medium, high); rollback note: if any regression test fails after an edit, restore v1.0 from the shared prompt library, trigger is a failed test in weekly production sampling.

The test case that catches a careless edit: input a sample email appealing a denied benefit, and require the output to return category "benefits" with the urgency key present and a summary of three sentences or fewer. If someone edits the prompt and drops the urgency instruction, the JSON arrives without that key and the test fails before the edit ships. If the edit lets summaries sprawl to five sentences, the length check fails. That is a tripwire, not a hope.

Posted in chat in the capture format: "citizen-email-summarizer/v1.0 | input: email_text (raw citizen email), output JSON {summary ≤ 3 sentences, category: benefits/permits/complaint/other, urgency: low/medium/high} | test: a benefit-appeal email must return category benefits with urgency present; the test fails if an edit drops the urgency field." Replying to a colleague, the most common missing field is the rollback note: naming v1.0 as the restore point and the failed-test trigger is what turns the header from documentation into change control.
