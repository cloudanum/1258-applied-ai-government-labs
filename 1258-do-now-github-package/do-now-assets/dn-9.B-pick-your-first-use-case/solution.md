# Sample / solution

## Why this approach works
The three-part template works because each part kills a different way first projects die. The plain-sentence use case keeps scope routine and text-heavy, the kind of work staff already do many times a week with a predictable shape. The named user, "permit intake staff" rather than "the agency," is what makes adoption, training, and feedback someone's actual job. The measurable result carries a baseline and a target, "from 2 days to same day," which turns the pilot into a claim leadership can verify, and the no-harm clause, "with no increase in corrections," stops a speed win from quietly becoming a quality loss. A weaker answer like "use AI to improve customer service" fails all three tests: no routine task, no daily user, and no number to defend. The instinct being built is scope discipline, boring on purpose beats impressive on a slide.

## A complete solution
The full chat post, in the capture format from the run steps:

`Use case: Draft first-pass responses to routine permit status questions. | User: Permit intake staff. | Measurable result: Median first-response time drops from 2 days to same day with no increase in corrections.`

Read aloud, the defense sounds like this: "This is a first use case because the work is repetitive and text-shaped, permit status questions arrive daily with the same structure. The user is a named team that would touch the tool every day, not a vague org unit. And the result has a baseline, a target, and a guardrail metric, so we do not trade accuracy for speed and can defend the whole thing to a CIO in one sentence." The step-6 review skill matters too: a good one-line reply to a peer is "strong first use case, named user and a metric with a baseline; consider adding a guardrail metric like correction rate," while "AI to modernize our permitting program" earns the correction "not yet a use case, which routine task and which daily user would you start with?"
