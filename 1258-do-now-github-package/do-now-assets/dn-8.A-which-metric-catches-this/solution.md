# Sample / solution

## Why this approach works
Matching the metric to the failure mechanism, not to the nearest familiar column, is what makes the placement defensible. A monitoring plan only catches what it measures, and a single global accuracy score stays reassuringly green while fairness gaps, silent drift, doubling latency, and tripled token bills all burn uncounted underneath it. The weaker instinct is to reach for accuracy whenever the answer content is involved, and it fails three different ways on this board: M6's answers are correct, so accuracy never trips on the missing citations; M4's refusals are usually scored as safe behavior, so accuracy rewards the over-blocking; and M8 needs a comparison against the retrieved source, which no answer-key accuracy metric can supply in production where no labels exist. Three of the eight stickies, M4, M6, and M8, fit none of the five supplied columns, and recognizing that the dashboard itself is incomplete is part of the lesson, not a placement error.

## A complete solution
Take M6: answers are correct but often lack the required citation. The wrong instinct is accuracy, since the content is right. The defense of the correct family: the failure is not what the answer says but whether it complies with the sourcing rule, and the metric that catches it is groundedness, measured as citation coverage, the percent of published answers carrying a valid citation to an approved source. An accuracy score cannot see this failure at all, because by construction the answers are accurate; only a metric that checks provenance per answer will move. The same logic places M8 under faithfulness: retrieval returned the right document, so retrieval metrics are green, but the final paraphrase is not supported by that document, and a faithfulness metric, does every claim in the answer trace to the retrieved text, catches the whole class without needing a human-labeled answer key.

The full placement: M1 to fairness (a language-slice metric, English versus French, because a global score averages the gap away); M2 to latency (p95 doubling after launch is an operational regression); M3 to drift (week-to-week answer changes after a model update call for version stability tracking); M4 to false-refusal rate, outside the five columns; M5 to cost (cost per request or a token budget metric); M6 to groundedness/citation coverage, outside the five columns; M7 to fairness (a geographic slice metric, one neighborhood far lower); M8 to faithfulness, outside the five columns.

The remote chat post reads: "M1-fairness, M2-latency, M3-drift, M4-false-refusal rate, M5-cost, M6-groundedness, M7-fairness, M8-faithfulness. Missing metric on our dashboard: cost per request (monthly token spend divided by requests served); we track uptime and a global satisfaction score, so the M5 failure, a 3x token bill at flat usage, would reach us only through the finance office." If a neighbor insists M1 is an accuracy problem, the defense is the mechanism: a global accuracy number can hold steady while the French slice fails, so only a per-slice fairness metric catches it first.
